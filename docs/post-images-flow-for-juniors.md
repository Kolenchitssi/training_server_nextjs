# Как работает сохранение картинок поста

## Зачем этот документ

Этот документ объясняет полный путь картинки:

1. как backend принимает файл в запросе
2. как файл проверяется
3. как формируется имя
4. как файл записывается на диск
5. как путь сохраняется в БД
6. как frontend показывает картинку в сохраненном посте

Документ соответствует текущей реализации в проекте.

## 1) Что отправляет frontend

Frontend отправляет multipart/form-data на endpoint:

- POST /api/post/:id/images

Поле с файлами должно называться images.

Можно отправить от 1 до 5 файлов за один запрос.

## 2) Как контроллер принимает файлы

В контроллере используется FilesInterceptor.

Что он делает:

1. достает файлы из multipart/form-data
2. кладет их в параметр метода как массив
3. ограничивает количество файлов в одном запросе
4. ограничивает максимальный размер одного файла

После интерсептора контроллер дополнительно валидирует:

1. массив не пустой
2. тип каждого файла только image/jpeg или image/png
3. размер каждого файла не больше MAX_UPLOAD_SIZE_MB

Если валидация не проходит, контроллер возвращает 422.

## 3) Во что превращается файл внутри backend

На практике библиотека multer возвращает объекты с данными файла.

В проекте мы используем свой тип UploadedBinaryFile:

1. buffer: бинарное содержимое файла
2. mimetype: MIME-тип, например image/jpeg
3. originalname: исходное имя файла пользователя
4. size: размер в байтах

Важно: originalname не используется как имя файла на диске.

## 4) Что проверяет сервис перед сохранением

В PostService метод uploadPostImages делает проверки в таком порядке:

1. существует ли пост
2. принадлежит ли пост текущему пользователю
3. не будет ли превышен лимит 5 картинок у поста

Лимит 5 работает в двух местах:

1. на уровне одного запроса (в контроллере)
2. на уровне общего количества картинок у поста (в сервисе)

Это важно, потому что пользователь может отправить несколько запросов подряд.

## 5) Как формируется имя файла

Для каждой картинки имя формируется так:

- postId + '-' + UUID + расширение

Пример:

- 7-f4f36273-3ab8-4b6a-b495-e6df2f3678cd.jpg

Плюсы такого подхода:

1. уникальность
2. нет конфликтов имен
3. нет проблем с браузерным кешем при перезаливке
4. исходное имя пользователя не влияет на storage

## 6) Как файл пишется на диск

PostService вызывает FilesService.saveFile, а тот делегирует в LocalStorageService.

LocalStorageService делает следующее:

1. определяет расширение по mimetype:
   - image/jpeg -> jpg
   - image/png -> png
2. формирует ключ в формате folder/fileName.ext
3. в нашем случае folder это posts
4. итоговый ключ выглядит так:
   - posts/7-f4f36273-3ab8-4b6a-b495-e6df2f3678cd.jpg
5. создает папки при необходимости
6. записывает файл через writeFile

Физически файл сохраняется в папку uploads (по умолчанию), то есть:

- project-root/uploads/posts/<имя-файла>

## 7) Что сохраняется в БД

После успешной записи файлов на диск backend создает записи в таблице post_images.

Для каждой картинки сохраняется:

1. post_id
2. path

Пример path:

- posts/7-f4f36273-3ab8-4b6a-b495-e6df2f3678cd.jpg

Очень важно:

- в БД хранится только относительный путь (ключ)
- полный URL не хранится

## 8) Как backend формирует URL

Есть два сценария:

1. Сразу после upload endpoint возвращает imageUrls.
2. При чтении поста backend возвращает path из post_images.

Почему статический URL вообще работает:

- в main.ts подключена раздача статики из папки uploads
- публичный префикс по умолчанию /uploads

То есть путь из БД posts/abc.jpg превращается во внешний URL:

- /uploads/posts/abc.jpg

## 9) Как frontend показывает картинку в сохраненном посте

### Вариант A: сразу после загрузки

Используем imageUrls из ответа upload endpoint.

### Вариант B: при загрузке поста позже

Когда frontend получает пост с массивом images, у каждого элемента есть path.

Frontend собирает URL так:

1. берет базовый URL API/сайта, например http://localhost:5001
2. добавляет /uploads/
3. добавляет path из БД

Итоговая формула:

- imageUrl = BASE_URL + '/uploads/' + image.path

Пример:

- BASE_URL = http://localhost:5001
- image.path = posts/7-f4f36273-3ab8-4b6a-b495-e6df2f3678cd.jpg
- итог = http://localhost:5001/uploads/posts/7-f4f36273-3ab8-4b6a-b495-e6df2f3678cd.jpg

## 10) Что происходит при ошибках

### Ошибка во время сохранения файлов на диск

Если часть файлов уже сохранена, а потом один из файлов упал, сервис удалит уже сохраненные новые файлы этого запроса.

Это уменьшает риск "мусора" в storage.

### Ошибка при записи в БД

Если файлы уже записаны на диск, но createMany в БД упал, сервис удалит только что сохраненные файлы.

Так не остаются сиротские файлы от неуспешной операции.

## 11) Короткая памятка для junior

1. Backend принимает files в поле images.
2. Проверяет тип, размер, количество.
3. Проверяет владельца поста.
4. Генерирует уникальные имена postId-uuid.
5. Сохраняет файлы в uploads/posts.
6. Пишет относительные пути в post_images.path.
7. Frontend строит URL через /uploads + path.

Если следовать этим шагам, поток сохранения и отображения картинок будет предсказуемым и безопасным.

## 12) Типичные ошибки frontend и как быстро исправить

Ниже самые частые проблемы, которые возникают при интеграции.

### Ошибка 1: отправили не multipart/form-data

Симптомы:

1. backend не видит files
2. приходит ошибка, что файлы не переданы

Почему так:

- запрос отправлен как application/json

Как исправить:

1. использовать FormData
2. каждый файл добавлять через formData.append('images', file)
3. не сериализовать FormData в JSON

### Ошибка 2: неправильное имя поля

Симптомы:

1. files пустой
2. upload endpoint возвращает ошибку валидации

Почему так:

- backend ожидает поле images, а frontend отправляет image, files или другое имя

Как исправить:

1. использовать строго имя поля images

### Ошибка 3: вручную проставили Content-Type

Симптомы:

1. boundary в multipart сломан
2. backend не может корректно распарсить тело

Почему так:

- в fetch/axios вручную указан заголовок Content-Type: multipart/form-data

Как исправить:

1. не задавать Content-Type руками при отправке FormData
2. дать браузеру/клиенту выставить заголовок автоматически

### Ошибка 4: слишком много файлов

Симптомы:

1. 422 при отправке
2. или ошибка в сервисе при превышении общего лимита поста

Почему так:

1. за раз отправили больше 5 файлов
2. либо у поста уже есть картинки и новый запрос превышает суммарно 5

Как исправить:

1. ограничить выбор на frontend до 5
2. перед upload показывать пользователю, сколько еще файлов можно добавить

### Ошибка 5: неподдерживаемый тип файла

Симптомы:

1. 422 с сообщением о типе файла

Почему так:

- разрешены только image/jpeg и image/png

Как исправить:

1. фильтровать файлы до отправки
2. показывать подсказку: "Только JPG/PNG"

### Ошибка 6: файл больше лимита

Симптомы:

1. 422 с ошибкой размера файла

Почему так:

- файл больше MAX_UPLOAD_SIZE_MB

Как исправить:

1. проверять file.size на клиенте до отправки
2. показывать понятный текст про лимит в MB

### Ошибка 7: забыли авторизацию

Симптомы:

1. 401/403 на upload endpoint

Почему так:

- не передан Bearer токен или токен невалиден

Как исправить:

1. добавлять Authorization: Bearer <token>
2. проверять, что токен актуальный

### Ошибка 8: картинка не отображается после успешного upload

Симптомы:

1. upload прошел, но в UI битая картинка

Почему так:

1. неверно склеили URL
2. забыли префикс /uploads
3. используют path как абсолютный URL без BASE_URL

Как исправить:

1. строить URL по формуле: BASE_URL + '/uploads/' + image.path
2. убедиться, что в main.ts включена раздача статики из uploads

## 13) Мини-чеклист перед релизом frontend

1. endpoint: POST /api/post/:id/images
2. формат тела: FormData
3. имя поля файлов: images
4. типы файлов: только JPG/PNG
5. лимиты: не больше 5 файлов и не больше MAX_UPLOAD_SIZE_MB на файл
6. токен: Bearer присутствует
7. рендер URL: BASE_URL + '/uploads/' + image.path
